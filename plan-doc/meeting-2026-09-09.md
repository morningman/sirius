## 3. 议题一 · 架构对齐（15 min）

### 3.1 对照表（可直接投屏）

| | **A · 伪 BE/CN 进程**（他们的 StarRocks 路线） | **B · BE 进程内子树卸载**（我们的选择） |
|---|---|---|
| 侵入宿主代码 | 零 | 小，且可摘除（默认关闭） |
| 内表 | **不可能** | 天然支持 |
| 复用宿主能力 | 全部失效（runtime filter / colocate / bucket shuffle / spill / 内存追踪） | 全部保留 |
| 协议外壳成本 | StarRocks CN ≈ 4600 行，且随宿主版本线性增长 | 0 |
| Doris 的表面积 | `PBackendService` **60+ 个 RPC** + AgentService + 心跳汇报 + runtime filter merge/publish + load stream | 一个头文件 |
| 版本耦合 | pin 死（他们 pin 在 StarRocks 4.1.1） | Substrait + Arrow，两边独立演进 |
| 崩溃隔离 | 天然 | 需要边车化（MVP-3 前后切） |

**要说清楚的一句话**：那 9000 行 Rust 里，**查询执行是 0 行**——4600 行是协议外壳，
3400 行是 plan 翻译。协议外壳是纯阻抗匹配、零业务价值，且成本随宿主协议表面积线性增长。
在 Doris 上，这个表面积是 StarRocks CN 的数倍。

### 3.2 对他们讲收益（这一段比讲我们的需求更重要）

1. **这条路把 Sirius 变成一个真正可嵌入的引擎，收益不是 Doris 独享的。**
   架构图第三格的 Spark SQL / Trino / DataFusion，走的都是同一个口子：
   一个能被 dlopen 的库 + Substrait 进 / Arrow 出 + C ABI。今天 Sirius 只有
   "DuckDB 扩展"和"伪 CN"两种形态，缺的正是第三种。
2. **不需要改引擎内部一行。** 三个缺口全在 FFI 和构建层。
3. **我们出人写。** （见 §4.3——这是今天最有分量的一张牌。）

### 3.3 预判他们的三个反问 + 回法

| 他们会问 | 怎么回 |
|---|---|
| "为什么不先做个伪 CN 拿数字？" | 不反对，但要说清定位：那条轨的产物是 **demo**，不是产品，而且拿不到内表。见 §5.3 的两轨方案 |
| "进程内会不会把 BE 搞崩？" | 会。所以默认关闭 + `SiriusTransport` 抽象 + MVP-3 前后切边车（ADR-010 已定）。这是我们自己的风险，不需要你们承担 |
| "`Context` 是单线程契约" | **这正是今天要解开的第一个结**（M1）。`stream_session::push` 本身是 mutex 保护的，S1 不变式就是为这个存在的，多次触发的 source（#836）当初也是为"边跑边喂"设计的 |

## 4. 议题二 · #1590 的具体推进（15 min）

### 4.1 诉求清单（按优先级，带估算）

| P | 诉求 | Sirius 侧规模 | 依赖 | 备注 |
|---|---|---|---|---|
| **P0** | `Fragment::push_arrow(stream, sender, ArrowSchema*, ArrowArray*)` | ~150 行生产 + ~230 行测试 | T5b | 纯 FFI 胶水；`cudf::from_arrow_host` 已在依赖闭包里（cudf 26.06 带 nanoarrow 0.7.0），只是全树没人用；**不动 cuCascade** |
| **P0** | libsirius 交付标准（四条链接约束 + install target + Release 产物） | ~150–250 行 CMake/YAML | — | 构建可在 CPU runner 验证，不需要 GPU |
| **P1** | C ABI `sirius_c.h` + `sirius_abi_version()` | ~800 行 shim | push_arrow | 纯外壳，不动内部；**异常跨两套运行时实测必崩**，所以它不是"可选优化" |
| **P1** | 配置安全阀 | ~50 行 | — | 默认独占 **95% 显存 + 每 NUMA 节点 90% 内存做 pinned**，撞 Doris 的 `mem_limit` 90%。嵌入时必须强制显式配置 |
| **P2** | `capabilities()` 能力查询 | ~100 行 | — | 消除白名单双写漂移 |
| **P2** | `HUGEINT` 静默截断改为报错 | ~10 行 | — | `cudf_utils.hpp:169`，代码里自带 `FIXME: silently corrupted`。**这是正确性 bug**，也是最适合的第一个 PR |
| **P2** | 结果路径 `to_arrow_host`（4 次拷贝 → 1 次） | ~120 行 | — | 顺手的性能改进，对所有宿主都有效 |

**合计：≈1.2–1.3k 行生产 + 0.6k 测试 ≈ 2–3 个工程周。**

### 4.2 四条链接约束（M3 的具体内容，要念清楚）

1. 依赖全静态 + `-fvisibility=hidden` + `--exclude-libs,ALL`
2. **`-static-libstdc++ -static-libgcc`** ← 这条是关键，没有它前面三条都没用
3. version script 只导出 `sirius_*`
4. libgomp 静态或移除、cuVS 可选化

**证据（被质疑时直接给）**：Doris BE 因为要服务 native UDF 而 `ENABLE_EXPORTS`，
导出 **475,722** 个符号，其中静态 libstdc++ 就有 50,662 个。真实 Sirius 产物预加载进去，
**687 个符号绑到了 BE 的私有副本上，其中 549 个是 libstdc++**。
90 例合成矩阵证明：conda 口味产物进 `-rdynamic` 宿主**必崩**；全静态 + 隐藏 + 静态 libstdc++ **完全免疫**。
`RTLD_DEEPBIND` 不是答案（malloc 分裂）。

> 一句话版本：**今天的 `sirius.duckdb_extension` 不能直接当 libsirius 用**，
> 它今天能在我们的实验里工作，靠的是 Doris 那份 libstdc++ 副本恰好够新——这不是可以依赖的。

### 4.3 关键动作：把"诉求"变成"贡献"

明确提出：**这些 Sirius 侧的补丁，我们出人写，你们只需要 review。**

配套要确认的三件事：
- CI 里的 `gpu-2xt4` self-hosted runner 会不会跑外部贡献者的 PR？（`push_arrow` 的测试打

- 期望的 PR 拆分粒度（他们 CONTRIBUTING.md 有 PR reviewability 清单和 stacked PR 规矩，我们照办）
- 排在 T5b 之后还是可以并行独立提

## 7. 议题五 · 用户案例与需求对齐（10 min）

### 7.1 先问，再说（这一段以听为主）

1. StarRocks 那条线背后有没有 design partner？是谁在推、什么负载、什么规模？
2. 他们见过的真实客户诉求里，GPU 数据库的**采购理由**是什么——是延迟、是成本、还是机房里
   本来就有闲置 GPU？
3. TPC-H SF500 只跑了 15 条，剩下 7 条卡在哪里？（这决定我们选案例时的算子边界）

### 7.2 必须说破的一个错配

**Sirius 今天的赢面在 parquet / lakehouse；Doris 用户的主力在内表。**

- 他们的 4.43× 是 TPC-H SF500 在 8×A100 上跑出来的，数据是 parquet
- Doris 内表要变快，唯一途径是 `doris_segment_gpu_ingestible`
  （GPU 解码 segment v2：bitshuffle / RLE / FOR / dict、page 索引、zone map、delete bitmap、MOW）——**数人年**
- → **第一批联合用户案例必须从 lakehouse 场景选**（Hive / Iceberg / Paimon 的 parquet 外表），
  这也正好是 MVP-3 的射程

### 7.3 三类候选负载（用他们自己的 break-even 判据筛）

| 负载 | 为什么可能赢 | 风险 |
|---|---|---|
| **Lakehouse 大表聚合 / 多表 join 报表**（Iceberg/Hive parquet） | compute/scan 比高，MVP-3 后 H2D 不在关键路径 | 需要算子覆盖到 join |
| **高并发 ad-hoc 探查**（金融风控、日志分析） | 单查询延迟敏感，GPU 优势明显 | **卡在 Sirius 的串行执行**（#1303），这是硬阻塞 |
| **向量检索 + SQL 混合**（Sirius 刚合并 IVF-Flat #1205，Doris 4.x 也在做 ANN） | 差异化，两边都有在建能力，故事新 | 双方能力都不成熟，作为探索性话题提 |

### 7.4 选案例前先过 gate（这份拒绝表要带着）

Doris 用户高频使用、但 Sirius 今天**不支持**的东西：
`LARGEINT`（静默截断，最高优先级）、`DECIMAL256`、`DECIMAL(p≤4)`、
`HLL` / `BITMAP` / `QUANTILE_STATE` / `AGG_STATE`、`JSONB` / `VARIANT`、
`IPV4` / `IPV6` / `VARBINARY` / `TIMESTAMPTZ`、`ARRAY` / `MAP` / `STRUCT`、
倒排索引相关能力。

**语义差异**：`concat` 的 NULL 语义不同（硬拒绝）、`like` 只接受常量且不含转义、
`substring` 只接受常量正 start/len。

> 选任何用户案例之前先过这张表，否则会承诺一个跑不起来的场景。

### 7.5 部署门槛（对齐预期，这条很实在）

Sirius 要求：Linux、计算能力 7.5+、CUDA 13.x（驱动 ≥580.65.06）或 12.x、**glibc ≥ 2.28**、
io_uring 可用（容器要放行 seccomp）、parquet 落在支持 `O_DIRECT` 的设备上。
运行时要带 **1 GB+ 的 CUDA 库**。

**Doris 用户里相当一部分还在 glibc < 2.28 的老系统上——他们直接出局。**
这一条会上要讲，它会影响用户案例的选择，也是"为什么必须默认关闭 + 优雅降级"的现实理由。

## 附录 B · 事实卡片（被问到时直接答）

**我们的调研**
- 提案：#1590 评论，2026-09-01；❤️ 来自 mbrobbel 和 aocsa；7 天无书面回复
- Doris BE 导出 475,722 个符号（`ENABLE_EXPORTS`，`be/src/service/CMakeLists.txt:68`，为 native UDF 服务，不会取消）
- 真实产物预加载实测：687 个符号绑到 BE，其中 549 个 libstdc++；**protobuf / abseil / arrow 绑定数为 0**
- 90 例合成矩阵：conda 口味 × `-rdynamic` 宿主 = abort；全静态+隐藏+静态 libstdc++ = 免疫
- C++ 异常跨两套运行时 = 必崩（所以 C ABI 是必需品，不是优化）
- `GNU_UNIQUE` 符号 58 个 → DSO 不可卸载（Doris 惯例本来就是永不 `dlclose`）

**工作量**
- `push_arrow`：~150 生产 + ~230 测试，不动 cuCascade
- C ABI shim：~800 生产
- libsirius target：~150–250 行 CMake/YAML
- Sirius 侧合计：≈1.2–1.3k 生产 + 0.6k 测试 ≈ 2–3 工程周
- Doris 侧嵌入运行时：≈0.7k（进程内）/ 1–1.5k（边车）

**他们的数字（deck）**
- TPC-H SF500，单机 8×A100 80GB（massedcompute，$13.25/hr，640 GB 显存，1500 GB 内存）
- 15 of 15 完成，套件 23.02s vs StarRocks 101.91s = **4.43×**
- 成本 break-even = **1.50×**；最好 q16 = 12.70×；**q01 = 1.14×，低于 break-even，照样放在图上**
- 架构：一 CN 一 GPU，NIXL over RDMA 替换默认 exchange，FE 的解析/优化/调度不变

**Sirius 现状**
- Maintainers：19 人（NVIDIA 14 / UW-Madison 3 / 其他 2）；Apache-2.0；GOVERNANCE 写明目标是进中立基金会
- CI：self-hosted GPU runner，label `gpu-2xt4`
- 运行要求：glibc ≥ 2.28、CC 7.5+、CUDA 13.x（驱动 ≥580.65.06）或 12.x、io_uring、`O_DIRECT`
- 默认独占 95% 显存 + 每 NUMA 节点 90% 内存做 pinned
- 无背压是**设计决定**（#1276，2026-07-23 review 结论）——不要再要，自己做限流
- 引擎进程内串行，一个 Context 同时一个 query（#1303 / #1583 在推进）

## 附录 C · 预期管理话术（提前说，别等被问）

主动说这三句，会让后面的合作省很多事：

1. **"MVP-1 的 benchmark 会很难看，我现在就说。"**

   任何对外材料，双方各自只讲自己那一半。
